# Career Quest — инструкции для работы с репозиторием

## Назначение

Веб-приложение развития сотрудников для кейса Halyk Bank: кабинет сотрудника,
рекомендации следующих шагов, прогресс навыков и HR-аналитика. Основной приоритет —
качество и объяснимость рекомендаций. Требования продукта описаны в `analysis.md`,
запуск и демо-аккаунты — в `README.md`.

## Архитектура

- Backend: Python standard library, HTTP-сервер и SQLite.
- `backend/app/web.py`: HTTP API, авторизация запросов и раздача страницы.
- `backend/app/static/`: HTML, CSS и JavaScript интерфейса.
- `career.py`: детерминированный расчёт навыков и карьерной траектории.
- `recommendations.py`: допустимые активности, AI-селектор и резервные правила.
- `importer.py`, `hr.py`: импорт JSON/CSV и HR-срез.
- `activities.py`: запись, завершение и персональный сброс демо.
- `bootstrap.py`, `demo_seed.py`: инициализация и пять демо-аккаунтов.
- `backend/migrations/`: последовательные SQL-миграции.

Проверяй текущий код перед изменениями: план и история обсуждения могут отличаться
от состояния checkout. Не меняй стек без необходимости для текущей задачи.

## Правила продукта и данных

- Сотрудник имеет доступ только к профилю, связанному с его сессией. HR-операции
  требуют роли `hr`. Проверяй права на сервере, а не только в интерфейсе.
- Используй синтетический набор `data/career_quest_dataset/` и сохраняй его схему.
  Перед изменением расчётов прочитай README набора. Дата демо — `2026-10-01`.
- Отсутствующий навык имеет уровень 0. Применяй `gain` и `max_level` только для
  завершённых активностей после последней оценки; не начисляй прирост повторно.
- Уровни, требования и прогресс считает сервер. LLM выбирает только допустимые
  `event_id`, не выдумывает мероприятия, числа и факты истории.
- До AI-выбора проверяй аудиторию, prerequisites, расписание и историю прохождений.
  Повторное участие в `EV_036` разрешено правилами стартового набора.
- Рекомендации должны учитывать несколько факторов. Ошибка модели не должна
  блокировать кабинет: используй явно обозначенный резервный режим.
- Импорт атомарный: неверный пакет не должен частично менять базу. Повторный
  идентичный импорт безопасен; конфликтующие исходные данные нельзя молча заменить.
- Новые изменения схемы оформляй отдельной нумерованной миграцией, совместимой
  с существующей базой. Не переписывай уже применённые миграции.
- Симуляция завершения и персональный сброс доступны только демо-сотрудникам
  при `DEMO_MODE=true`. Сброс удаляет только их данные, созданные приложением,
  сохраняя исходную историю, импорт жюри и данные других сотрудников.
- Не добавляй публичные рейтинги сотрудников или награды за обязательные процессы.
  HR-сигналы участия нужны для поддержки, а не оценки результативности.

## Безопасность и рабочий процесс

- Не читай, не печатай и не коммить значения `.env` или API-ключи. Для документации
  используй имена переменных и заглушки. Ключ модели остаётся на сервере.
- Сохраняй изменения пользователя; не выполняй сброс Git или базы без запроса.
- При изменении интерфейса добавляй состояние загрузки, обработку ошибок и защиту
  от повторного нажатия. Не заставляй весь кабинет ждать ответа AI.
- Поддерживай README в соответствии с фактическими командами и поведением.

## Проверка

После изменений backend:

```bash
python3 -m unittest discover -s backend/tests -v
```

После изменений входа, bootstrap, HR или демо-сценария:

```bash
python3 scripts/acceptance.py
```

После изменений JavaScript проверяй синтаксис и затронутый сценарий в браузере:

```bash
node --check backend/app/static/app.js
```

Запуск для жюри при наличии Docker:

```bash
docker compose up --build -d
docker compose ps
```

В новых тестах используй комплектный датасет и временную базу, без абсолютных
путей к компьютеру разработчика. Не подменяй проверку настоящего AI тестовым
селектором в отчёте. Указывай, какие проверки выполнены, а какие недоступны.
