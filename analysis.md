# Анализ кейса: Agentic AI для прогнозирования выработки ВЭС

Предлагается строить решение вокруг **воспроизводимого прогноза на 48 часов с ежедневным обновлением, проверкой доступности данных и журналом решений агента**. Для жюри нужно показать три вещи: модель даёт измеримое качество, прогноз не использует информацию из будущего, система самостоятельно реагирует на обновления и ошибки.

Самый важный технический риск — **архивные прогнозы погоды**. Его нужно закрыть до разработки сложной модели и интерфейса.

Ниже — последовательный план с целями, задачами и критериями готовности. Это план реализации; качество модели можно будет оценить после получения файлов.

## 1. Зафиксировать правила прогнозирования

**Цель:** однозначно определить, что прогнозируем и какие данные разрешено использовать.

Что сделать:

- Получить исторические файлы и описание колонок.
- Установить часовой пояс и значение временной метки: начало или конец интервала.
- Проверить частоту измерений и правила перевода в почасовые значения.
- Уточнить, что означает нормализированная мощность и как выполнена нормализация.
- Определить, представлены данные отдельно по двум турбинам или суммарно по ВЭС.
- Получить номинальные мощности и, по возможности, высоту ступицы.
- Зафиксировать ежедневное время выпуска прогноза и допустимую задержку поступления измерений.
- Уточнить, будут ли в ходе февральского моделирования доступны фактические измерения за уже прошедшие дни февраля.

Последний пункт принципиален. Если доступны только данные до 31 января, нельзя использовать фактическую мощность за 1 февраля при прогнозе от 2 февраля. В таком случае основной прогноз должен работать на погоде и фиксированной исторической модели.

Нормализованная мощность также не равна энергии в МВт·ч. Для перевода необходимы параметры нормализации и мощности оборудования. Если нормализация выполнена относительно номинала:

`энергия за час = нормализованная средняя мощность × номинальная мощность × 1 час`.

**Результат:** документ с правилами расчёта и конфигурация ВЭС. Координаты из коротких ссылок нужно отдельно извлечь и проверить: в ходе проверки ссылки не раскрылись.

- [Турбина 2](https://maps.app.goo.gl/8UQMwsYavY6nLvFY8)

## 2. Подтвердить доступность правильного архива погоды

**Цель:** получить прогнозы, реально существовавшие на момент каждого исторического выпуска.

Нужно различать:

| Данные | Применимость к задаче |
|---|---|
| Фактическая погода и реанализ | Не подходят в качестве будущей погоды в тестовом прогнозе |
| Архив, склеенный из первых часов разных запусков | Сам по себе не воспроизводит прогноз на 48 часов, выпущенный в один момент |
| Архив конкретного запуска погодной модели | Подходит при проверке времени его доступности |

Кандидат для первой проверки — **Open-Meteo Single Runs API с ECMWF IFS HRES**. Документация заявляет архив отдельных запусков с марта 2024 года; для остальных моделей этого API архив начинается со 2 апреля 2026 года, то есть позже тестового периода. Наличие нужных переменных, происхождение исторических запусков и условия доступа необходимо проверить пробной загрузкой. [Документация Single Runs API](https://open-meteo.com/en/docs/single-runs-api).

Обычный Historical Forecast API склеивает начальные часы последовательных запусков. Его нельзя автоматически считать историческим прогнозом на следующие двое суток. [Описание Historical Forecast API](https://open-meteo.com/en/docs/historical-forecast-api).

Что сделать:

1. Скачать один запуск для конца января 2026 года и обеих координат.
2. Проверить наличие следующих 48 часов.
3. Запросить скорость и направление ветра на доступных высотах, температуру; дополнительные параметры — по наличию.
4. Проверить покрытие обучающего периода и всего февраля.
5. Зафиксировать источник, модель, единицы измерения и способ пространственной интерполяции.
6. Сохранить исходные ответы в локальный архив.

Для каждого погодного значения хранить:

| Поле | Значение |
|---|---|
| `model_run_at` | Время инициализации погодной модели |
| `available_at` | Когда результат стал доступен, либо документированная консервативная оценка |
| `valid_at` | Час, на который дан прогноз |
| `retrieved_at` | Когда мы скачали архив |
| `source`, `model` | Источник и погодная модель |

Ключевое правило: **`available_at ≤ forecast_issued_at`**. Время инициализации модели не означает, что её результаты уже опубликованы.

**Критерий готовности:** воспроизводимая загрузка одного полного исторического прогноза с доказуемым соблюдением временных ограничений.

## 3. Провести аудит и подготовку данных ВЭС

**Цель:** получить надёжную почасовую обучающую таблицу.

Что сделать:

- Найти пропуски, дубликаты и нарушения временного порядка.
- Проверить диапазоны мощности, ветра и температуры.
- Построить графики мощности во времени и зависимости мощности от скорости ветра.
- Выделить подозрительные остановки, ограничения мощности и ошибки датчиков.
- Привести данные к согласованной временной шкале.
- Сохранять признаки качества данных, а не только очищенные значения.

**Не удалять все нули при сильном ветре:** они могут отражать реальные остановки. Если задача — прогноз фактической выдачи в сеть, такие режимы влияют на целевую величину.

При подготовке исторических признаков нельзя интерполировать значения с использованием измерений, которые на момент выпуска ещё не поступили.

**Результат:** очищенный набор, отчёт о качестве и явно описанные правила обработки.

## 4. Создать простые модели для сравнения

**Цель:** получить точку отсчёта, относительно которой можно доказать пользу ML.

Реализовать:

- Прогноз последним известным значением мощности — с учётом его давности.
- Повтор предыдущих суток — только там, где соответствующие измерения доступны.
- Эмпирическую кривую мощности: зависимость мощности от ветра, обученную на истории и применённую к прогнозному ветру.

Все модели должны получать информацию по одним временным правилам.

Для первой проверки использовать несколько последовательных временных разбиений до февраля, например осенние месяцы 2025 года и январь 2026 года. Случайное перемешивание строк здесь не подходит.

**Результат:** таблица ошибок простых моделей и первый работающий сквозной прогноз.

## 5. Обучить основную модель

**Цель:** улучшить качество на отложенных временных периодах.

Практичный первый вариант — **CatBoost или LightGBM**, выбранный по результатам валидации.

Одна строка обучающей таблицы:

`момент выпуска × турбина × прогнозируемый час`.

Признаки:

- Прогнозные скорость и направление ветра.
- Прогнозная температура.
- Горизонт прогноза в часах.
- Возраст погодного запуска.
- Час суток и сезонные признаки.
- Идентификатор турбины.
- Последние измерения мощности и ветра, если они разрешены и доступны.
- Давность последних измерений.

Обучать основную модель нужно на **архивной прогнозной погоде**, соответствующей историческим моментам выпуска. Обучение только на фактическом ветре с последующей подстановкой прогнозного создаёт несоответствие между обучением и применением.

Если подходящий погодный архив начинается в 2024 году, более ранние данные ВЭС можно использовать для анализа режимов и кривой мощности. Не нужно искусственно достраивать отсутствующие исторические прогнозы фактической погодой.

После базового результата добавить:

- Квантили P10/P50/P90 для оценки неопределённости.
- Коррекцию систематического смещения прогнозного ветра.
- Сравнение общей модели для двух турбин с отдельными моделями.

Интервалы проверять на валидации: доля наблюдений между P10 и P90 должна соответствовать заявленному покрытию. Интервал суммарной ВЭС нельзя корректно получить простым сложением квантилей турбин.

**Критерий готовности:** модель сравнили с базовыми подходами по одинаковому протоколу, а её ограничения документированы.

## 6. Реализовать агентный цикл

**Цель:** система самостоятельно выбирает допустимые действия, проверяет результат и восстанавливается после сбоев.

Достаточно **одного управляющего агента с инструментами и сохраняемым состоянием**. Несколько отдельных агентов для MVP необязательны.

Последовательность:

`Событие → проверка состояния → получение погоды → подготовка признаков → прогноз → проверка → сохранение → объяснение результата`.

| Компонент | Что делает |
|---|---|
| Управляющий агент | Выбирает следующий шаг по состоянию данных и результатам проверок |
| Инструмент погоды | Получает допустимый запуск, использует кэш, повторяет временно неудачные запросы |
| Проверка данных | Контролирует временные ограничения, полноту и единицы |
| Инструмент модели | Загружает зафиксированную версию и рассчитывает прогноз |
| Проверка результата | Проверяет количество часов, диапазоны, пропуски и порядок квантилей |
| Хранилище | Сохраняет прогноз, версии входов и историю решений |

LLM можно использовать для выбора действий из ограниченного набора и объяснения результатов. **Численные прогнозы и проверки временной доступности выполняет код.**

Обязательные сценарии:

- Пришла новая допустимая погода → создать новую версию прогноза.
- Погодный API недоступен → повторить запрос, затем использовать допустимый кэш.
- Есть только устаревший прогноз → проверить покрытие горизонта и явно отметить его возраст.
- Нет допустимых данных → показать невозможность расчёта, не подставлять будущую информацию.
- Повторное событие с теми же входами → не создавать дубликаты.

В историческом режиме «новая погода» определяется симулируемым временем, а не текущим временем компьютера.

**Критерий готовности:** журнал показывает не только успешный запуск, но и хотя бы одну осмысленную ветку восстановления.

## 7. Воспроизвести февраль 2026 года

**Цель:** получить полный набор прогнозов без утечки из будущего.

Что сделать:

1. Зафиксировать модель и настройки после валидации.
2. Последовательно перемещать виртуальное время по ежедневным моментам выпуска.
3. На каждом шаге открывать только уже доступные данные.
4. Выпускать прогноз на 48 часов.
5. Сохранять все версии, включая перекрывающиеся прогнозы на один час.
6. Оценивать только целевые часы февраля; мартовские часы сохранять отдельно.

В феврале 2026 года **672 часа**. При ежедневных выпусках на 48 часов прогнозных строк будет больше из-за перекрытий.

Заранее определить, как формируется итоговый файл: например, отдельные результаты для следующих календарных суток и вторых суток. Нельзя выбирать лучший прогноз постфактум.

Рекомендуемые метрики:

- MAE — средняя абсолютная ошибка.
- RMSE — чувствительность к крупным ошибкам.
- Bias — систематическое завышение или занижение.
- Отдельные ошибки для горизонтов 1–24 и 25–48 часов.
- Покрытие и ширина интервалов неопределённости.

MAPE не стоит брать основной метрикой: при нулевой выработке она становится проблемной.

**Если фактической мощности за февраль нет, февральские метрики посчитать нельзя.** Тогда сдаём прогнозы за февраль, а качество показываем на исторической валидации.

## 8. Подготовить воспроизводимый запуск

**Цель:** жюри может повторить результат без ручной настройки отдельных ноутбуков.

Предлагаемый стек: Python, pandas/Polars, CatBoost или LightGBM, Parquet, SQLite и Streamlit для демо.

В репозитории должны быть:

- README с постановкой задачи, архитектурой и командами запуска.
- Конфигурация координат, времени выпуска и источников.
- Зафиксированные зависимости.
- Команды подготовки данных, обучения, исторического прогона и запуска демо.
- Модель и описание её обучающего периода.
- Результаты валидации.
- Итоговый CSV прогнозов.
- Журнал происхождения погодных данных.
- Разрешённые к распространению примеры и инструкция получения остальных данных.

Особенно важные автоматические проверки: запрет будущих данных, корректные часовые пояса, полнота 48 часов, отсутствие повторных записей и восстановление из кэша.

**Критерий готовности:** запуск из чистого окружения по README воспроизводит контрольный пример.

## 9. Сделать демо для жюри

**Цель:** за 5–7 минут показать весь сценарий и доказательства его корректности.

Экран демо:

| Блок | Что показываем |
|---|---|
| Виртуальное время | Момент, «в котором» сейчас находится система |
| ВЭС | Две турбины и подтверждённые координаты |
| Погода | Источник, запуск, время доступности и возраст |
| Прогноз | Почасовой график на 48 часов, турбины и агрегат при известной нормализации |
| Неопределённость | Проверенный интервал прогноза |
| Агент | Выполненные действия и причины решений |
| Качество | Сравнение с простыми моделями на доступной фактической выборке |
| Экспорт | CSV и журнал расчёта |

Сценарий выступления:

1. **Проблема — 30 секунд.** Почему планирование ВЭС требует почасового прогноза и оценки неопределённости.
2. **Исторический запуск — 1 минута.** Устанавливаем момент 31 января, показываем выбранную погоду и её доступность.
3. **Результат — 1 минута.** Получаем прогноз на 48 часов и выгружаем таблицу.
4. **Обновление — 1 минута.** Продвигаем виртуальное время до публикации следующего запуска. Агент пересчитывает прогноз, показывает изменения и сохраняет прежнюю версию.
5. **Сбой — 1 минута.** Имитируем недоступность API. Демонстрируем допустимый кэш и объяснение решения.
6. **Доказательства — 1–2 минуты.** Показываем качество, временные проверки и воспроизводимость.

Для защиты подготовить локальный кэш реальных архивных ответов и резервную видеозапись. В интерфейсе явно указывать, когда данные взяты из кэша.

## Порядок приоритетов

| Приоритет | Задачи | Связь с оценкой |
|---|---|---|
| P0 | Корректный архив погоды, правила времени, сквозной прогноз, февральский прогон | Соответствие задаче — 25 баллов |
| P0 | Агентный цикл, проверки, обновления и восстановление | Техническая реализация — 25 |
| P0 | README, фиксированные зависимости, повторяемый запуск | Воспроизводимость — 25 |
| P1 | Сравнение моделей, интервалы, экспорт и удобное демо | Практическая ценность — 15 |
| P2 | Несколько погодных источников, адаптивная коррекция, расширенная диагностика | Развитие и оригинальность — 10 |

Первые три направления соответствуют **75 из 100 баллов**, поэтому их стоит довести до готовности прежде, чем добавлять сложные модели.

**Первый рабочий рубеж:** один подтверждённый исторический погодный запуск → простая модель → 48 почасовых значений → CSV → журнал, доказывающий отсутствие данных из будущего. После этого можно последовательно улучшать качество и превращать рабочий процесс в убедительное демо.
