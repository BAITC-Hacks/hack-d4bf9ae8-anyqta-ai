# Career Quest — анализ ТЗ и план разработки

## 1. Цель и границы решения

Разрабатываем веб-приложение Career Quest для сотрудников и HR в рамках кейса Halyk Bank на HackAlem AI. Сотрудник авторизуется, видит карьерную траекторию, получает 1–3 обоснованных шага развития, выполняет активность и видит изменение навыков. HR авторизуется в отдельном кабинете и видит дефициты компетенций и показатели участия.

Формат веб-приложения соответствует ТЗ. Voice Router — отдельный кейс, в эту разработку не входит. Главный результат — качество и объяснимость рекомендаций, а не количество экранов или игровая механика.

Основные разделы сохраняют исходный план. Фактическая реализация и границы проверки зафиксированы в разделе 13; текущие команды запуска находятся в README.

### Источники и происхождение требований

- Основа: предоставленное пользователем ТЗ Career Quest и стартовый набор `case_1/career_quest_dataset` с README.
- Требования пользователя: авторизация, роли сотрудник/HR, 3–4 демо-сотрудника разных уровней, один HR и понятный README для самостоятельного запуска жюри.
- Принятое решение: подготовить **4 демо-сотрудника — Junior, Middle, Senior, Lead — и 1 HR**.
- Предлагаемые технические решения и правила продукта явно описаны ниже; они не являются дополнительными требованиями организаторов.

## 2. Обязательная функциональность и ограничения

### По ТЗ

1. Профиль сотрудника и траектория развития относительно карьерной цели и требований грейда.
2. От 1 до 3 рекомендаций с объяснением на основе нескольких факторов.
3. Точный пересчёт навыков и прогресса после завершения активности.
4. HR-экран с проседающими компетенциями и сигналами выпадения из развития.
5. Импорт дополнительных профилей и истории в формате датасета: жюри загружает проверочные данные на защите.
6. Разграничение доступа сотрудник/HR, защита индивидуальных данных от других сотрудников.
7. Отклик интерфейса до 2 секунд; AI-рекомендация до 10 секунд.
8. Репозиторий, README, запуск одной командой.

### По запросу пользователя

- Настоящий вход в приложение с серверной проверкой роли.
- Заранее подготовленные демо-аккаунты: четыре сотрудника разных грейдов и один HR.
- README с простым запуском всех сервисов, адресом веб-страницы, логинами и паролями.
- Полный сценарий самостоятельной проверки для жюри.

### Не включать в обязательный MVP

Внутреннюю валюту, магазин наград, признание от коллег, конструктор событий, прогноз оттока, интеграции с календарями и мессенджерами. Локализация на русский и казахский, расширенная аналитика и мобильная адаптация — последующие улучшения. Для первой версии предлагаем русский интерфейс.

### Ограничения ТЗ

- Нельзя выдавать рекомендацию по одному полю за AI-анализ.
- Нельзя делать публичный рейтинг результативности сотрудников.
- Нельзя строить игровую механику вокруг обязательных процессов.
- Нельзя использовать реальные персональные данные.
- Участие в рекомендованных активностях добровольное.
- Данные синтетические; ТЗ ограничивает их использование рамками хакатона. Комплект передачи жюри должен содержать разрешённый датасет или точную инструкцию его локального размещения, без зависимости от компьютера разработчика.

## 3. Проверенные входные данные

| Файл | Содержимое | Назначение |
|---|---|---|
| `employees.json` | 200 профилей | Роль, грейд, навыки, карьерная цель, дата оценки |
| `skills.json` | 60 навыков; 32 профиля требований — 8 ролей × 4 грейда | Требования и критические навыки для целевой позиции |
| `events.json` | 40 мероприятий, из них 4 обязательных | Аудитория, prerequisites, прирост навыков, расписание |
| `activity_history.csv` | 2 743 записи за 24 месяца | Завершения, участие, пропуски, отказы и прекращение обучения |

JSON-файлы содержат объекты с `meta` и именованными массивами (`employees`, `events`, `skills`, `role_profiles`), а не массивы в корне. Импорт должен сохранять совместимость с этой схемой.

Правила из README набора:

- Дата среза и «сегодня» для демо: **2026-10-01**. Не использовать текущие часы компьютера для отбора сессий в этом режиме.
- История: с 2024-10-01 по 2026-09-30.
- Отсутствующий в профиле навык равен 0; допустимые уровни — 0–5.
- Навыки в профиле соответствуют последней оценке `last_review_date`.
- Завершённые после последней оценки активности ещё не учтены в навыках профиля.
- `gain` и `max_level` задают прирост и потолок навыка для конкретного мероприятия.
- Обязательные активности (`mandatory=true`) не являются объектом рекомендаций развития.
- Завершённое мероприятие не повторяется, кроме регулярного клуба `EV_036`.
- Для `self_paced` пустое расписание означает доступность в любое время.

В CSV поле `date` для self-paced означает дату зачисления, отдельного времени завершения нет. Для исторического пересчёта принять и документировать допущение: у завершённых записей использовать `date` как доступную временную отметку. Для новых завершений хранить отдельное `completed_at`; не заявлять точность времени завершения, которой нет в исходных данных.

Учётных записей, паролей и ролей доступа в датасете нет. Должность сотрудника `role` и роль доступа `access_role` — разные сущности. Должность HR Business Partner сама по себе не предоставляет права HR.

## 4. Предлагаемая архитектура

Для MVP: React + TypeScript для интерфейса, FastAPI для API и рекомендательного слоя, PostgreSQL для хранения, Docker Compose для общего запуска. Это предлагаемая архитектура; версии зависимостей и образов нужно зафиксировать при реализации.

Сервисы:

- `web`: интерфейс и проксирование `/api` к серверу, единый адрес приложения.
- `api`: авторизация, импорт, расчёты, рекомендации, завершения и HR-аналитика.
- `db`: PostgreSQL с постоянным томом.
- `init`: одноразовая миграция, импорт стартовых данных и создание демо-аккаунтов перед готовностью API.

Основные сущности: пользователи, сотрудники, навыки, требования ролей и грейдов, события, история участия, журнал применённых изменений навыков, рекомендации и результаты импорта.

Схема рекомендации:

`Профиль + история → актуальные навыки → разрывы до цели → допустимые события → LLM → серверная проверка → 1–3 шага с объяснениями`.

Расчёты и ограничения выполняет код. LLM сопоставляет факторы и объясняет выбор, но не назначает произвольные уровни навыков.

## 5. Правила траектории и рекомендаций

### Цель и прогресс

- Использовать `career_goal`, если он задан, включая смену роли.
- Если цели нет, предложить следующий грейд текущей роли: Junior → Middle → Senior → Lead.
- Для Lead без заданной цели не выдумывать следующий грейд: предложить выбор цели и развитие доступных навыков.
- Разрыв по навыку: `max(0, требуемый уровень − актуальный уровень)`.
- Отдельно показывать разрывы по `critical_skills`.
- Предлагаемый общий показатель: доля покрытых уровней целевых требований, `sum(min(current, required)) / sum(required) × 100%`. Если требований нет, показывать «цель не задана», а не делить на ноль.
- Этот показатель отражает покрытие требований по навыкам, а не вероятность или гарантию повышения.

### Пересчёт после завершения

Для каждого развиваемого навыка:

```text
новый уровень = max(текущий уровень,
                    min(5, max_level, текущий уровень + gain))
```

Событие не должно понижать навык, уже превышающий его потолок. Учитывать только `completed`, применять записи последовательно по времени и не начислять прирост дважды. Исторические завершения до или на дату оценки не прибавлять повторно. Для клуба учитывать отдельные участия, а не повтор одного запроса.

### Отбор кандидатов

Проверять роль и грейд аудитории, prerequisites, расписание, отсутствие уже завершённого или текущего участия, добровольность и полезный прирост. При смене карьерной роли учитывать цель, но не обходить ограничения аудитории события. Если полезный следующий шаг требует подготовки, объяснить цепочку prerequisites.

### Многофакторный выбор

Учитывать дефициты до цели, критичность навыков, ожидаемый прирост, длительность, историю завершений/пропусков/отказов, формат и доступность. Повторяющиеся пропуски — основание предложить другой формат, а не автоматически исключать сотрудника из развития.

Ответ должен содержать реальные `event_id`, объяснение выбора, текущий и требуемый уровни, ожидаемый прирост и использованные факты истории. Проверять ответ по данным на сервере. Если подходящих событий нет, честно показать причину вместо выдуманной рекомендации.

При отказе LLM использовать явно обозначенный резервный подбор по правилам. Он обеспечивает работоспособность демо, но не заменяет проверку настоящего AI-слоя.

## 6. Экраны и доступ

| Экран | Содержание | Доступ |
|---|---|---|
| Вход | Логин, пароль, понятные ошибки | Неавторизованный пользователь |
| Мой рост | Профиль, цель, навыки, разрывы, рекомендации | Сотрудник — только свой профиль |
| Активность | Польза, prerequisites, расписание, формат, длительность, запись | Сотрудник |
| Моя история | Участия, статусы, изменения навыков | Сотрудник — только своя история |
| HR-обзор | Дефициты навыков, участие, фильтры по отделу/роли/грейду | HR |
| Карточка сотрудника для HR | Траектория и основания сигналов поддержки | HR |
| Импорт | Загрузка, валидация, предварительный результат, отчёт | HR |

Права проверяются сервером для каждого запроса; скрытия кнопок недостаточно. Пароли хранить в виде хешей, сессии — с безопасными настройками cookie, секреты не включать в Git.

HR-сигналы должны быть объяснимыми: например, отсутствие завершённых добровольных активностей за выбранный период или повторяющиеся пропуски. Не называть их оценкой эффективности или прогнозом увольнения. Порог и период показывать в интерфейсе.

## 7. Демо-аккаунты: четыре сотрудника и один HR

Создать аккаунты автоматически при инициализации демо. Выбрать реальные синтетические профили из стартового набора, закрепить их `employee_id` в seed-конфигурации и связать с аккаунтами. Грейд, навыки и историю выбранных профилей проверить заранее. Если для нужного сценария требуется дополнительная фикстура, пометить её как синтетическое расширение и сохранить схему датасета.

| Логин | Роль доступа | Грейд | Сценарий |
|---|---|---|---|
| `junior@careerquest.demo` | employee | Junior | Понятный первый шаг к Middle; видимый прирост после завершения |
| `middle@careerquest.demo` | employee | Middle | Разрыв по критическому навыку до Senior; история влияет на выбор |
| `senior@careerquest.demo` | employee | Senior | Развитие до Lead с учётом требований выбранной роли |
| `lead@careerquest.demo` | employee | Lead | Корректная обработка верхнего грейда и отсутствующей/другой карьерной цели |
| `hr@careerquest.demo` | hr | Не определяет права | Аналитика, просмотр профилей и загрузка проверочных данных |

Предлагаемые публичные пароли исключительно для локального демо: `DemoEmployee2026!` для четырёх сотрудников и `DemoHR2026!` для HR. Итоговый README должен содержать фактически работающие значения и связанные профили. Эти аккаунты создаются только при `DEMO_MODE=true`; вне демо публичные пароли не используются.

Критерии готовности:

- Все пять аккаунтов работают сразу после первого запуска без регистрации и ручного изменения БД.
- Четыре сотрудника имеют разные грейды и показывают осмысленные, проверенные сценарии.
- Аккаунт сотрудника не открывает чужую историю или HR API даже при подмене URL/ID.
- Повторный запуск не дублирует аккаунты, историю и приросты и не стирает текущий прогресс.
- Есть отдельная документированная команда возврата к исходному состоянию демо.

## 8. Этапы разработки и критерии готовности

### Этап 1. Модель данных и импорт — начать здесь

Задачи:

- Создать каркас репозитория, схему БД и миграции.
- Написать импорт всех четырёх файлов с поддержкой исходных JSON-обёрток.
- Проверять идентификаторы, связи, диапазоны уровней, даты и статусы.
- Сделать повторный импорт без дублей и понятный отчёт об ошибках.
- Поддержать добавление проверочных профилей и истории к существующим каталогам.
- При совпадающих ID явно показывать конфликт и режим обновления; не перезаписывать данные молча. Ошибочный пакет не должен частично менять БД.

**Готово:** стартовый датасет загружается; новый профиль с историей добавляется тем же механизмом; повторный импорт безопасен.

### Этап 2. Расчётное ядро

Задачи: восстановить актуальные навыки, определить цель, вычислить разрывы и покрытие требований, показать происхождение приростов. Учесть Lead, смену роли и отсутствие навыков.

**Готово:** по `employee_id` возвращаются проверяемые навыки, цель, требования и дефициты. Завершения не учитываются дважды.

### Этап 3. Допустимые активности и AI

Задачи: фильтрация кандидатов, многофакторный выбор, структурированный ответ LLM, серверная валидация, таймаут и обозначенный резервный режим. Кэш привязать к версии профиля, истории и каталогов; после изменений инвалидировать.

**Готово:** рекомендации не нарушают ограничения, объясняют пользу и учитывают историю; проверены неоднозначные профили, на которых правило «минимальный навык» ошибается.

### Этап 4. Авторизация и seed демо

Задачи: вход/выход, сессии, серверные права, привязка аккаунтов к профилям, создание пяти демо-пользователей. Предварительно проверить пригодность выбранных профилей для защиты.

**Готово:** можно войти каждым аккаунтом, ограничения доступа работают, повторная инициализация не создаёт дубли.

### Этап 5. Кабинет сотрудника

Задачи: профиль, цель, сравнение навыков с требованиями, карточки рекомендаций, детали событий и история. Предусмотреть состояния загрузки, ошибки и отсутствия подходящих активностей.

**Готово:** сотрудник понимает следующий шаг, его пользу и ожидаемый эффект.

### Этап 6. Выполнение и обновление прогресса

Задачи: запись на событие, демонстрационное завершение, транзакционное обновление истории, навыков и рекомендаций. Кнопку симуляции разрешить только в демо-режиме и явно подписать. Интеграция с реальной LMS не требуется для MVP.

**Готово:** работает цепочка «рекомендация → активность → завершение → прирост → новая рекомендация»; повторный запрос не меняет результат повторно.

### Этап 7. HR и загрузка данных жюри

Задачи: срез дефицитов, критические навыки, фильтры, объяснимые сигналы поддержки и UI импорта JSON/CSV. После импорта обновлять аналитику и рекомендации. Для нового профиля дать HR возможность открыть траекторию и рекомендации без создания аккаунта и редактирования БД.

**Готово:** HR самостоятельно загружает профиль и историю жюри и сразу показывает результат.

### Этап 8. Запуск всех сервисов и README

Задачи: завершить Docker Compose, healthchecks, порядок миграций и seed, конфигурацию LLM, адрес веб-приложения, диагностику и сброс демо. Каркас запуска заложить на этапе 1, финальную проверку выполнить здесь.

**Готово:** новый участник поднимает приложение по README без помощи автора, входит всеми пятью аккаунтами и проходит демо.

### Этап 9. Приёмка и репетиция защиты

Задачи: проверить расчёты, права, импорт новых данных, сложные рекомендации, отказ модели, время отклика и восстановление начального состояния.

**Готово:** весь сценарий защиты воспроизводится на чистом окружении; ограничения и режим работы честно описаны.

## 9. Требования к README и воспроизводимому запуску

README — обязательный артефакт для жюри. Он должен описывать реально проверенные команды, а не ссылаться на окружение разработчика.

### Быстрый старт

Целевой основной запуск после получения репозитория и доступного стартового набора:

```bash
docker compose up --build -d
```

Команда должна поднять БД, выполнить миграции и seed, запустить API и веб-интерфейс. Не требовать локальной установки Node.js, Python или PostgreSQL. Предварительное требование — Docker с Compose и доступ к образам/зависимостям для первой сборки; это явно указать.

Адрес реализованного демо: `http://127.0.0.1:8000`. В README размещены ссылка и команда проверки готовности `docker compose ps`.

### Два явно различимых режима

1. **Демо без внешнего ключа:** после одной команды доступны авторизация, данные, HR, импорт и завершения. Рекомендации работают в обозначенном резервном режиме; интерфейс прямо сообщает, что LLM не подключена.
2. **Полный AI-режим для оценки:** README показывает заполнение `.env` из `.env.example`, значения `LLM_API_URL`, `LLM_MODEL`, `LLM_API_KEY` и команду запуска/перезапуска. До защиты проверить реальные AI-рекомендации на подготовленных и новых профилях.

Не обещать полноценный AI без модели или ключа. Если выбирается локальная модель, отдельно документировать её загрузку, ресурсы и время подготовки. Конфигурацию модели согласовать до финальной упаковки; публичные пароли демо не являются ключами внешних сервисов.

## 10. Сценарий финального демо

Ориентир — 5–7 минут; все аккаунты доступны жюри для самостоятельной проверки.

1. **Запуск:** показать раздел Quick Start в README, состояние сервисов, адрес страницы и таблицу аккаунтов.
2. **Junior:** войти, показать цель и понятный следующий шаг развития.
3. **Middle:** показать рекомендацию, где критический навык и история важнее самого низкого навыка. Объяснение должно опираться на реальные факты выбранного профиля.
4. **Прогресс:** симулировать завершение подходящей активности, показать точный прирост и обновление рекомендаций.
5. **Senior и Lead:** кратко показать разные траектории и корректную обработку верхнего грейда без фиктивного повышения.
6. **HR:** войти отдельным аккаунтом, показать дефициты компетенций, фильтры и основания сигналов поддержки.
7. **Проверочные данные:** загрузить новый профиль и историю в HR-разделе, открыть его рекомендации без изменения кода.

Перед защитой восстановить исходное демо-состояние. Не подменять реальные AI-ответы заранее написанными объяснениями; если используется резервный режим, явно обозначить его.

## 11. Проверки и приоритеты

## 13. Доработки после повторной сверки ТЗ — 2026-09-23

Реализован один сервис на Python standard library + SQLite и веб-интерфейс
на JavaScript. Порт 8000. Выполнены следующие доработки:

1. Сотрудник и HR, включая импортированные профили, используют один сервис
   рекомендаций. HR видит обоснования, прогноз и источники истории.
2. AI получает профиль без имени, описание и навыки кандидатов, историю за год
   по пересекающимся навыкам. Модель может выделить только проверенные факторы.
3. Импорт проверяет роли/цели, целочисленные уровни, CSV-строки, завершённость
   и конфликты ID. Предварительная проверка ничего не сохраняет. Итоговый импорт
   повторно проверяет пакет в транзакции и возвращает новые/повторные записи.
4. Профиль и AI загружаются отдельно. Кэш ограничен по размеру и времени,
   инвалидируется версией данных; устаревший ответ после изменения данных не выдаётся.
5. Добавлены три синтетических профиля и сравнение с минимальным навыком.
   Реальная модель проверяется отдельно через `--with-ai`; unit-тесты с
   подставным селектором не являются оценкой её качества.
6. Все тесты используют комплектный датасет. HTTP-приёмка работает на временной
   базе. Команда сброса запускается без права исполнения скрипта и проверяет
   режим запущенного контейнера. Healthcheck проверяет БД.
7. Есть выбор цели, все требования, последовательный прогноз и фактические
   изменения после завершения. Личная цель не меняет исходный импортированный JSON.
8. HR видит доли критических дефицитов по отделам, 12 месяцев добровольного
   участия и исходную историю. Рейтинги сотрудников не добавлены.

Подтверждены локальные тесты, HTTP-сценарий и проверка алгоритма на трёх
подготовленных профилях. Docker и настоящий провайдер AI в этом окружении
не проверялись. Они остаются частью репетиции на машине защиты.
